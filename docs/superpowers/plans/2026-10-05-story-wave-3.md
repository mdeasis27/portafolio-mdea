# Story Pages Wave 3 Implementation Plan

> **For agentic workers:** execute natively (Manuel chose native for the rollout). Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Turn ensayo, destilacion, veredicto, arbitro and escaneo ("compare two options") into story pages built like Compuerta's, each with a bet a visitor can lose.

**Architecture:** Same page and shared pieces as Waves 1–2 (`pnpm brand:sync` from the hub; all five are behind and lack `outcome-tape`, `project-story`, `flow-diagram`, `copy-lint`). Unlike Wave 2, each engine already works over a **real fixed set** (cases, documents, questions, tasters), so the tape is the engine's own items. One slider per page grades that set.

**Tech Stack:** Next.js 16, TypeScript strict, Tailwind v4, vitest. All five have a Python `backend/`; Python changes only where the engine itself changes (ensayo data, escaneo `level`), pinned by the existing shared fixtures.

**Spec:** `docs/superpowers/specs/2026-10-04-project-story-pages-design.md`. Master plan: `2026-10-05-story-pages-rollout.md`. References: `../compuerta`, `../bandera` (range slider), `../doorman` (batch revealed in groups).

## Global Constraints

- Prerequisites on `main`: backup PR #1 of each of the 5 repos. Branch per repo: `feat/story-page` from `origin/main`. Hub branch: `feat/story-wave-3`.
- Page order, copy rules, `why.text = ""`, `lintStory` clean, no brands, no `any`/`@ts-ignore`, money in integer cents: as in Waves 1–2.
- Old controls (textareas, selects, presets, per-judge sliders) leave the page. Existing adapters, API routes and their tests stay unchanged.
- Python is touched only where the engine changes; every such change is pinned in both TS and Python by the shared fixture.
- A classifier deny is a wall: stop and report BLOCKED.

## Review Focus

1. **Bet that can't lose:** a sweep test per project over its slider proving both answers, and the default answer in the table.
2. **Bet text out of sync:** `question(value)` names the slider value; the grade reads the same quantity.
3. **Tape vs result:** final tape counts equal the engine counts.
4. **Parity:** ensayo and escaneo fixtures byte-identical in TS and Python and read by both suites.
5. **Honesty:** "For engineers" says which parts are TS-only (arbitro tape, destilacion cents, veredicto retrievers) and that ensayo's 40 tasters are a fixed synthetic set.
6. **Mobile:** 390px, no horizontal overflow.

## Per-project decisions (from the read-only sweeps, 2026-10-05)

| Project | Slider (default) | Bet | Flip | Tape (N) | With / without | Engine change |
|---|---|---|---|---|---|---|
| **arbitro** | Confidence the judges need, 50–95% (60%) | "Needing 60% confidence, does the video referee review at most 4 of 22 plays?" | Yes ≤82%, no ≥83% | 22 cases: settled right / reviewed / settled wrong (16/4/2 at default) | With the referee vs plurality only: 2 wrong vs 4 | None: tape built in `lib/experience` from `arbitrate()` per case |
| **destilacion** | Requests per month, 10k–1M step 10k (250k) | "At 250,000 requests a month, is buying cheaper than renting?" | No ≤300k (300k is a tie, counts as no), yes ≥310k | 30 days: renting still ahead / crossover day / days overpaying | Rent cost vs buy cost in cents (existing comparison) | None: per-day cents in TS (`result.days`), TS-only like the cents adapter |
| **veredicto** | Passages read per question, 1–8 (3) | "Reading 3 passages per question, do all 21 answerable questions find their evidence?" | No ≤5 (q14 missed), yes ≥6 | 24 questions: found / out of scope / missed (20/3/1 at default) | Your k vs k = 8 | None: suite loop over the 24 questions in TS with the hybrid retriever (Python has no retrievers) |
| **ensayo** | Tasters, 5–40 (10) | "With 10 tasters, does the new recipe get approved?" | No at the default, yes at 40; exact flip pinned by test | One square per taster: prefers new / can't tell / prefers old | Statistical gate vs "ship if most tasters liked it" | **Data only:** new `exp-3` (40 tasters, small real lift) in both `prompts.json`; regenerate both `experiments.json` |
| **escaneo** | Checks the cashier runs, 0–5 (2) | "With 2 checks, are all 6 broken receipts held?" | No ≤2 (d09 bad date slips), yes ≥3 | 12 documents: accepted clean / held / accepted broken (6/5/1 at default) | Your checks vs all 5: 1 slipped vs 0 | `validateFields(f, level?)` and `validate_fields(f, level=None)`: checks in order format, allowlist, calendar, check-digit, Luhn; per-level outcomes added to both `benchmark.json` |

Notes:
- **ensayo:** the existing data cannot carry a natural bet (exp-1 always ships, exp-2 only flips at 70% confidence). `exp-3` must be built so that prefixes of 5–15 tasters hold and 40 advance; pick it by sweeping, then pin `analyze` on prefixes in a test. The p-value over prefixes need not be monotonic: the bet is about the slider's stops, and the sweep test checks both answers occur. The page states the confidence used (95%) in plain words.
- **escaneo:** fix the old "valid receipt" preset in the adapter test data (account has 11 digits and always fails `format`), since it misleads anyone reading the adapter.
- **arbitro:** c21 and c22 stay wrong until 89–90%: confident majorities overruling the right dissent. Say so in "For engineers" as the honest limit.
- **veredicto:** analogy changes from the master plan's "tasters with the same questions" (doesn't fit the k slider) to the exam one below.
