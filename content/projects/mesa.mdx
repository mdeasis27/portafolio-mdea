## El problema

Un pipeline de "agentes" que se pasan texto suelto de uno a otro se cae de tres maneras predecibles: un agente manda un payload que el siguiente no espera, la run se queda en bucle pidiendo revisiones para siempre, o el coste se dispara porque nadie puso un límite ejecutable. Las tres fallas son estructurales, no de calidad del modelo — y un system prompt amable no las arregla.

Mesa ataca esas tres: handoffs validados por schema, un presupuesto que detiene la run en código, y un subgrafo de revisor cuya terminación se puede probar.

## El enfoque

Un supervisor delega en tres especialistas (planner / researcher / writer) a través de handoffs tipados; un revisor puede devolver trabajo un número acotado de veces:

1. **Handoffs como schemas** — cada transición valida su payload (`{ queries, context }`, `{ findings, citations, topic }`) en runtime. Un handoff roto falla fuerte en el borde, no silenciosamente aguas abajo.
2. **Presupuesto en código** — sub-queries, tokens, pasos y wall-clock se chequean *antes* de cada paso. Cruzar un límite detiene el grafo con `BudgetExhaustedError`, sin excepciones sin manejar ni quema de tokens.
3. **Trace durable** — cada paso registra qué agente recibió qué, qué produjo, tokens y latencia. Un snapshot serializa la run para poder resumirla tras un crash.
4. **Revisor que termina** — el contador de rechazos es estrictamente creciente y acotado, así el grafo converge por construcción.

## Decisiones de diseño

<Tradeoff title="El presupuesto vive en código, no en el prompt">
Un límite pedido en el prompt es aspiracional: el modelo puede (y suele) ignorarlo. Chequear el límite antes de cada paso vuelve el agotamiento un resultado determinista. El costo es que los handlers deben reportar tokens/latencia honestamente — un contrato que la interfaz impone.
</Tradeoff>

<Tradeoff title="Terminación por contador, no por esperanza">
El subgrafo de revisor es el único lugar donde un loop de agentes puede girar para siempre. Acotar `reject_and_revise` con un contador estrictamente creciente es una garantía estructural, demostrable con el sweep, no una promesa de comportamiento.
</Tradeoff>

<Tradeoff title="Handoffs son schemas, no personas">
Los agentes pasan payloads tipados validados en runtime, no texto libre entre "personalidades". Es lo que hace la orquestación depurable: un handoff roto se detecta en el borde en vez de envenenar el estado compartido.
</Tradeoff>

## Estado actual

Demo funcional end-to-end: 39 tests de Vitest (TS) y 5 de pytest (Python), ambos contra el fixture compartido `orchestration.json`. Deployable en Vercel sin claves. Para producción:

- Handlers LLM reales detrás de la misma interfaz `MesaHandlers` (live mode)
- Tokenizer real para el accounting de tokens (la demo usa `len/4`)
- Resume real desde snapshot: reconstruir `RunState` desde el trace serializado
- Supervisión distribuida con reintentos por agente (hoy el grafo es secuencial)

## Lo que demuestra

Que "multi-agente" se gana o se pierde en el control flow, no en el modelo. Tipar los handoffs, meter el presupuesto en código y probar la terminación son tres decisiones de ingeniería que separan a quien dibuja diagramas de agentes de quien ha depurado una run que no terminaba.
