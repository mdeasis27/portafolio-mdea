## El problema

La seguridad de un sistema LLM se demuestra, no se declara. La mayoría de los equipos no tiene
un artefacto que ataque sus propias apps de forma repetible: corren un ataque una vez, se
convierte en un informe, y nadie verifica que el hueco siga cerrado después del fix. Sin dedupe,
el primer run fila cuarenta copias del mismo issue; sin una cola de review, todo lo dudoso se
esconde o se ignora.

Asedio ataca esas tres fallas: batería committed, three outcomes (pass / fail / needs-review),
y un loop de cero-regresiones.

## El enfoque

Target adapter interface (payload → response + metadata) para apuntar a apps propias, checks
deterministas primero, y severidad = exploitabilidad × impacto:

1. **Checks deterministas primero** — leak de system prompt, regex PII, herramienta bloqueada,
   URL saliente. Gratis e inequívocos: FP = 0 por construcción. Luego el clasificador de
   contenido dañino para lo que necesita interpretación.
2. **Three outcomes** — pass / fail / needs-review. La cola de review es donde el clasificador
   publica su tasa de falsos positivos en vez de esconderla.
3. **Dedupe por firma** — attack id + firma de respuesta (FNV-1a). Sin esto, un run fila 40 copias.
4. **Zero-regression** — todo finding confirmado se vuelve caso permanente; nada se elimina al
   corregirlo, así el re-run demuestra que el hueco sigue cerrado.

## Decisiones de diseño

<Tradeoff title="Determinista antes que juez">
Un leak de prompt o un PII son un match de regex, no una opinión. Poner los checks baratos e
inequívocos primero hace el harness reproducible y deja el clasificador solo para violaciones de
política que necesitan interpretación.
</Tradeoff>

<Tradeoff title="Three outcomes, no dos">
Un harness binario inunda el tracker o descarta lo dudoso. La cola de review es exactamente
donde se aprende qué se te escapa: el clasificador reporta su FP rate en lugar de fingir certeza.
</Tradeoff>

<Tradeoff title="Nada se elimina al corregir">
Cada finding confirmado se vuelve un caso de regresión permanente. El demo es el loop completo:
encontrar la vulnerabilidad, shippear el fix, y el siguiente run confirmando que sigue cerrada.
Ese loop es el punto entero del proyecto.
</Tradeoff>

## Estado actual

Demo funcional end-to-end: 22 tests de Vitest (TS) y 6 de pytest (Python), ambos contra los
fixtures compartidos `fnv/severity/stats.json`. Deployable en Vercel sin claves. Para producción:

- Batería garak/PyRIT + casos de dominio propios detrás de la misma interfaz
- Juez LLM real para la cola de review (el clasificador de keywords es un proxy documentado)
- Auto-file de findings vía GitHub API con repro mínimo
- Cobertura contra una taxonomía publicada (OWASP LLM Top 10)

## Lo que demuestra

Que safety es un control loop, no un informe: atacar la propia app, medir la neutralización y
probar que el hueco queda cerrado sin regresiones es lo que separa un checklist de un control.
